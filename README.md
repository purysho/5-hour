# Driftless

Detects breaking changes in upstream APIs and opens the fixing PR in downstream
codebases.

---

## The problem

When an API provider ships a breaking change, they announce it. A changelog
entry, a deprecation notice, an email. Then thousands of downstream codebases
quietly break, or freeze on an old version and never move again.

The cost lands in two places. Consumers burn engineering time on migrations
nobody wanted. Providers carry permanent version fragmentation, a support load
generated by customers stranded on versions they cannot afford to leave, and
churn from the ones who give up.

This is getting worse quickly, for a specific reason: models write code against
a snapshot of the world, and the world keeps moving. Generated code is written
against APIs as they were at training time and is increasingly broken on
arrival. The volume of code that needs maintaining is compounding, and the
amount of human attention available to maintain it is not.

## What Driftless does

1. **Detect.** Watch an upstream API or SDK for changes that break consumers —
   spec diffs, release artifacts, and registry metadata, corroborated across
   sources rather than trusted from one.
2. **Locate.** Identify the downstream codebases affected.
3. **Fix.** Generate the migration and validate it against the repository's own
   test suite.
4. **Open.** Raise a pull request, with the reasoning and the upstream change
   it derives from.

Driftless opens pull requests. It never merges them, and it never holds
permissions that would let it. Human review is a security control, not a
formality — see [ADR-0002](docs/adr/0002-zero-standing-privilege.md).

## Architecture

```
   upstream change signals                repository contents
   (spec diffs, releases,                 (code, docs, comments,
    registry metadata)                     issues, fixtures)
            │                                      │
            └──────────────┬───────────────────────┘
                           ▼
              ┌────────────────────────┐
              │  INGEST                │   all input is data,
              │  detect · corroborate  │   never instruction
              └────────────────────────┘
                           ▼
              ┌────────────────────────┐
              │  CONTROL PLANE         │   tenancy · scheduling
              │  durable workflows     │   policy · audit
              └────────────────────────┘
                           │  short-lived, single-repo token
                           ▼
              ┌────────────────────────┐
              │  RUNNER SANDBOX        │   kernel-isolated
              │  clone · patch · test  │   single-use, no secrets
              └────────────────────────┘
                           ▼
                  PULL REQUEST
                  (human review required)
```

Four properties this design exists to guarantee:

- **No standing access.** Credentials are minted per job, scoped to one
  repository, and expire in minutes. A breach of our database yields no
  repository access. ([ADR-0002](docs/adr/0002-zero-standing-privilege.md))
- **Untrusted content cannot become instruction.** Repository text is never
  interpolated into an instruction channel, and a successful injection finds no
  credential and no egress route.
  ([ADR-0003](docs/adr/0003-untrusted-repository-content.md))
- **Exactly-once writes.** A retry storm cannot open a second pull request; the
  guarantee is a database invariant, not application logic.
  ([ADR-0004](docs/adr/0004-durable-workflows-and-exactly-once-prs.md))
- **Independently verifiable actions.** Customers can verify what Driftless did
  in their repositories without trusting Driftless.
  ([ADR-0007](docs/adr/0007-tamper-evident-audit-log.md))

## Status

Foundation laid. The four guarantees above exist as code and are covered by
tests; the pipeline that uses them does not exist yet.

**Built and tested**

- Tenancy schema with row-level security, plus cross-tenant probes and a check
  that fails the build if a migration adds a `provider_id` table without RLS
- The exactly-once claim/resolve protocol, tested under concurrency and
  simulated worker death
- The instruction/data boundary, including a type that throws rather than
  being interpolated into a prompt
- The diff policy engine and its unified-diff parser
- The hash-chained audit log, with tamper detection proven by tampering as a
  superuser — bypassing the application entirely
- An adversarial corpus of injection attempts, wired as a blocking CI gate
- Durable job execution: leased dequeue, step memoisation, backoff, dead
  letters — tested against worker death, lease expiry and concurrent workers
- The outbound write guard: kill switch, per-installation ceilings, and the
  idempotency claim, checked in that order
- The GitHub App credential layer: per-job single-repository token minting
  through a signer the key never leaves, with a credential type that redacts
  on every implicit conversion
- The runner environment builder and egress allowlist — an allowlist rather
  than a denylist, verified by value shape as well as by name
- The migration workflow composing all of the above, tested end to end through
  the real queue and database with only the model and the forge injected
- The corroboration gate: a change reaches fan-out only when independent
  sources agree, weighted by how hard each is to forge

**Not built yet**

Change detection, downstream discovery, the runner sandbox, migration
generation, the GitHub App integration, and the dashboard.

## Getting started

Requires Node 22+ and Postgres 16.

```bash
pnpm install
createdb driftless_test
DATABASE_URL=postgresql://localhost/driftless_test pnpm db:migrate
pnpm test
```

The suite needs a live Postgres. That is deliberate: row-level security and the
idempotency invariant are database behaviour, and mocking them would test the
mock. Tests connect as a role that is a member of `driftless_app` rather than a
superuser, so RLS genuinely applies — running them as a superuser would make
every isolation assertion pass vacuously.
